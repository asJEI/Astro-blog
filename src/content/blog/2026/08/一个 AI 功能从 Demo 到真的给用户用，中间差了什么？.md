> Demo 能跑，和一个东西真的能给人用，中间可能隔着整个产品。

我以前很喜欢做 Demo。

一个想法冒出来，打开 Cursor，建项目，接 API，写 Prompt，调工作流。如果顺利的话，一个周末就能做出一个看起来还不错的东西——输入一个问题，AI 开始思考；几个 Agent 跑起来；最后页面上出现一份结构完整、看起来很聪明的答案。

那一刻很容易产生一种错觉：**这个产品已经做出来了。**

直到后来，我真的把一个 AI 功能交给了真实用户，我才慢慢意识到：**Demo 能跑，和一个东西真的能给人用，中间可能隔着整个产品。**

---

## 一、我以前是怎么做 AI 产品的

前段时间，我做过一个叫 [**OpenSource Mentor**](https://hokkai.top/) 的项目。它的起点其实很简单。

我自己刚开始接触开源的时候，经常面对一个 GitHub 仓库发呆。README 看完了，然后呢？代码应该从哪里开始读？这么多 Issue，我这种水平能做哪个？这个项目用了十几个我没见过的技术，我是不是应该先去学一遍？以及一个非常经典的问题：**「Good First Issue 到底哪里 Good 了？」**

所以我想做一个面向开源新人的 AI 导师。你把一个 GitHub 仓库交给它，它帮你分析项目结构、技术栈和代码；根据你的能力推荐适合参与的 Issue；告诉你应该先学什么；如果开始写代码了，还可以继续帮你做 PR Review。

我后来把它真正做了出来。仓库分析、Issue 推荐、学习路线、导师对话、PR Review……功能一个个加进去。当这些东西第一次完整跑通的时候，我其实挺兴奋的——因为从 Demo 的角度看，它已经成立了。

用户输入仓库，系统分析仓库，Agent 开始工作，最后生成一份漂亮的结果。Happy Path 完美闭环。如果是在 Hackathon 上，做到这里甚至已经可以录 Demo 视频了。说起来，OpenSource Mentor 里的 PR Review 能力，也确实延续了我之前拿去路演过的 AI PR Review 项目。

但现在回过头看，我会问另一些问题。如果用户扔进来的是一个巨型 Monorepo 呢？如果 README 已经过时了呢？如果仓库根本没有适合新人的 Issue 呢？如果用户连 Fork、Clone 和 Pull Request 分别是什么都不知道呢？如果 AI 推荐了一个看起来很合适、实际上根本不适合新人的 Issue 呢？如果仓库分析失败了呢？

以前的我最关心的是：**它能不能完成任务？** 现在我更关心的是：**它完成不了任务的时候怎么办？**

但说实话，当时做 OpenSource Mentor 的我其实还没有真正意识到这两个问题之间的差别。毕竟在自己的项目里，我既是开发者，也是测试人员，甚至还是那个最熟悉产品应该怎么使用的「用户」。我知道应该输入什么，也知道怎样才能让它跑出最漂亮的结果。

直到后来，我开始把另一个 AI 项目真正放到用户面前。然后用户开始不按剧本出牌了。

## 二、真实用户根本不会按照你的 Demo 来

后来在实习的时候，我开始参与一个面向海外用户的 AI 客服 Bot。一开始这件事情听起来也很简单——公司已经有 FAQ，那把 FAQ 整理出来归类成一个个方便查询的词条，让 AI 根据用户的问题找到对应答案，不就行了吗？

于是我开始整理知识库，最后做出了 54 条结构化 FAQ，覆盖 10 种语言。每条 FAQ 不再只是简单的：

> Question → Answer

而是逐渐加上同义表达、语言、Intent、Action、是否需要人工介入，以及需要进一步收集哪些信息。

然后真实用户来了。我发现了一件非常朴素的事情：**用户根本不会按照 FAQ 的方式提问。**

他们不会说：

> 「您好，我的云手机设备已经过期，请问应该如何续费？」

他们可能只发一句：

> bro why dead

可能拼错单词，可能用缩写，可能英语里混着印尼语，可能上一句话还在说支付，下一句话突然开始问游戏。甚至可能只发一张截图，然后一个问号：

> ?

更麻烦的是，有时候单看这一句话根本无法判断问题，答案藏在前面三轮对话、订单截图，甚至用户默认你已经知道的背景里。

这时候我第一次很明显地感受到：**你设计的是圆形接口，但用户拿着方形积木要塞进去。**

Demo 里的用户永远很配合。他们知道自己想问什么，也知道应该怎么问。真实世界不是这样。用户不会研究你的 Prompt，不知道你的 Intent 分类，更不会为了提高 Embedding 相似度主动把句子写规范一点。他只知道一件事：应用出问题了，你给我解决。

于是问题开始从「AI 能不能回答这个问题？」变成「AI 到底知不知道用户在问什么？」——这两件事情差得非常远。

## 三、能回答问题，不代表应该回答问题

最开始做 AI 项目的时候，我天然希望模型尽可能聪明。能回答 80% 的问题，就想办法做到 90%；能做三个任务，就想办法再加两个 Agent。能力越强越好。

但客服 Bot 给我的另一个教训是：**有些问题，AI 最正确的回答就是不要回答。**

比如订单异常，比如支付争议，比如账户问题，比如需要后台查询才能确认的信息。如果 AI 根本不知道真实订单状态，却根据 FAQ 自信地告诉用户：「您的订单已经完成。」那它语言表达得再自然，也没有意义。甚至越自然越危险。

于是整个系统开始出现另一套逻辑：

- FAQ 能确定的问题，直接回答
- 需要模型理解的问题，让模型处理
- 低置信度的问题，不猜
- 高风险的问题，不猜
- 需要后台数据的问题，转人工
- 信息不足的问题，先收集必要信息

以前我觉得 AI 产品最重要的是：**让 AI 知道更多。** 现在我越来越觉得，另一件同样重要的事情是：**让 AI 知道什么时候自己不知道。**

但问题并没有停在这里。后来我们讨论过一个更进一步的想法：既然每天都会产生大量真实用户的问题，其中还会不断出现 FAQ 没有覆盖、AI 无法确定、最终只能转给人工处理的情况，那这些「AI 不知道的问题」，是不是也可以反过来成为系统下一次迭代的数据？

比如每天结束后，让 AI 自动汇总当天的咨询记录，把反复出现的问题、没有命中 FAQ 的问题、低置信度的问题进行聚类和归纳，再生成新的 FAQ 候选。这样一来，知识库就不再是一份写完之后等着人维护的静态文档，而开始随着真实用户的问题不断变化。

听起来很美好。但这里马上又出现了另一个问题：**AI 可以自己发现知识缺口，但它应该有权限修改自己的知识吗？**

假如模型某一天错误理解了一批用户的问题，又把这个错误结论自动写进 FAQ，那么下一次，这就不再只是一次回答错误了。它可能会把这个错误当成「标准答案」，继续回答之后的用户。

所以真正合理的循环可能不是：

> 发现问题 → AI 自动修改 FAQ

而是：

> 用户提问 → AI 回答 → 记录失败/低置信度样本 → 每日汇总 → 问题聚类 → 生成 FAQ 候选 → 验证/人工审核 → 更新知识库 → 下一轮用户提问

AI 可以负责发现问题、整理问题，甚至提出解决方案。但在它真正改变生产环境里的知识之前，仍然应该存在一道边界。

这时候我才发现，「不知道」其实也不是一件坏事。如果一个 AI 产品能够记录自己不知道什么，那么这些失败本身，就可以成为下一次迭代的起点。

这时候我又想起了 OpenSource Mentor。如果它没有真正理解一个仓库，它应该给用户推荐 Issue 吗？如果它无法判断一个任务的实际复杂度，它应该告诉一个刚学 React 的新人：「这个 Issue 非常适合你」吗？如果它生成了一条错误的学习路线，而用户真的按照它学了两个星期呢？

但反过来，如果这些失败能够被记录下来呢？哪些仓库最容易分析失败？哪些 Issue 经常被推荐，却没有用户愿意真正尝试？新人拿到学习路线之后，究竟在哪一步放弃了？这些东西可能比「这一次 Agent 有没有成功跑完」更值得关注。

Demo 阶段，我很少认真考虑这些问题。因为 Demo 只需要证明：**AI 可以做到什么。** 而一个真正给用户使用的产品，还要回答另外两个问题：**AI 不应该做什么？** 以及——**当 AI 做不到的时候，产品能不能从这次失败里学到东西？**

## 四、「我测试过了」到底是什么意思？

以前做个人项目，我的测试方式非常简单。打开网页，点一下，能跑；再点一下，还能跑。OK，Ship it.

但一个东西真的准备给用户用之后，「我试了一下没问题」显然不够了。后来在客服 Bot 上，我开始建立自动化测试——正常问题、同义表达、不同语言、模糊表达、异常输入、需要转人工的问题、高风险问题。最后整理出了 37 项测试。

当然，37 个测试远远谈不上多。但它至少让我第一次开始认真思考一个问题：**我凭什么说这个 AI 功能「能用」？**

是因为我自己问了五个问题，它都回答对了吗？还是因为 Demo 视频里的三个 Case 都成功了？又或者，是因为我写的 37 个测试现在全部通过了？

后来我发现，这里面其实还有两件不同的事情。

**第一件事，是证明它有没有按照我的预期工作。** 用户问设备过期的问题，能不能找到正确的 FAQ？不同语言表达同一个问题，能不能识别出相同的 Intent？遇到高风险问题，会不会老老实实转人工，而不是自己编一个答案？这些东西可以通过测试不断验证。

**第二件事，是我的「预期」本身，真的是用户需要的吗？** 这一点，测试用例没有办法完全告诉我。

一个客服 Bot 可以通过所有测试，但如果用户的问题根本不在我的测试集里，它依然可能不好用。一个 Issue 推荐 Agent 也可以每次都成功返回十个 Issue，但如果用户一个都不想做，那它即使从来没有报过错，又有什么意义？

所以如果今天让我重新做 OpenSource Mentor，我想看的就不会只是：

- 仓库解析有没有成功？
- Agent 有没有正常运行？
- Issue 有没有成功返回？

我还会继续往后看：

- Issue 推荐到底准不准？
- 用户有没有点击推荐的 Issue？
- 推荐之后，有多少人真的开始尝试解决？
- 哪些仓库最容易分析失败？
- 哪些情况下 AI 最容易产生幻觉？
- 新人最常在哪一步卡住？
- 最终有没有人因为这个工具，完成自己的第一个 Pull Request？

因为如果这些东西都不知道，我其实很难回答：**OpenSource Mentor 到底有没有帮助用户参与开源？** 我只能证明：**OpenSource Mentor 能运行。** 而「能运行」和「有用」，是两回事。

这也是我现在越来越在意的一个区别：**测试是在验证产品有没有按照设计运行，而真实用户是在验证你的设计到底对不对。** 前者可以让我更有底气地说：「这个功能没有坏。」后者才能让我回答：**「这个功能到底有没有用？」**

## 五、上线之后，产品才刚刚开始

还有一个以前经常被我忽略的东西：**日志。**

这段时间我在公司听得最多的一句话之一，大概就是：**「先抓一下日志。」**

产品刚上线的时候还有不少 Bug。遇到问题，先复现；复现出来了，抓日志；然后再去看为什么报错、问题到底发生在哪一步。前几天我在复现一个 Bug 的时候，第一件事同样是被提醒：先把日志抓下来。

这件事听起来好像非常理所当然。但我后来想了一下，如果是以前做自己的项目，我处理 Bug 的方式通常不是这样的。页面炸了，打开终端，看一眼报错，改代码，再运行一次。好了，结束。

因为开发者是我，测试是我，用户还是我。我知道自己刚才做了什么，也知道问题大概发生在哪里。但当一个产品真的交给用户之后，这套方式突然就不够用了。

用户不会告诉你：

> 「我在调用某个接口的时候收到了一个 500，然后发现可能是这里的状态处理有问题。」

他只会告诉你：

> 「用不了。」

甚至很多时候，他什么都不会告诉你，只会留下一张截图。于是你不得不开始从系统留下来的痕迹里重新还原：**这个用户刚才到底经历了什么？**

而对于 AI 产品来说，这件事情甚至更加重要：

- 这个问题为什么没有命中 FAQ？
- 用户为什么被识别成了错误的 Intent？
- 是哪种语言的问题最多？
- 哪些问题总是需要人工介入？
- 模型当时为什么选择了这个答案？
- 有没有一种用户表达，是我们设计系统的时候根本没有想到的？

这些东西如果没有被记录下来，那么一次失败就真的只是一次失败。用户走了，问题消失了，然后下一次遇到同样的问题，再失败一次。

但如果这些失败能够留下痕迹，事情就不一样了。一个没有命中 FAQ 的问题，可以成为新的知识库候选。一次错误的 Intent 判断，可以成为新的测试 Case。一个反复出现的 Bug，可以帮助我们找到真正需要修复的地方。甚至那些被转给人工的问题，本身也可以告诉我们：**这个产品现在还不会什么。**

慢慢地，我开始建立一种新的理解。产品不是：

> 设计 → 开发 → 上线 → 完成

而更像是：

> 设计 → 开发 → 上线 → 用户开始搞事情 → 留下日志和数据 → 找到问题 → 修改 → 再上线 → 用户继续搞事情……

然后无限循环。

所以现在我越来越觉得：**用户不是产品最后的验收环节，用户本身就是产品开发的一部分。**

这一点对于 AI 产品尤其明显。传统软件很多时候面对的是相对确定的输入——按钮就是按钮，手机号就是手机号，日期就是日期。但大模型面对的是自然语言，而自然语言意味着几乎无限的表达方式。

你可以提前准备 37 个测试，可以整理 54 条 FAQ，可以尽可能考虑各种异常情况，但你永远不知道第 38 个 Case 会是什么，也永远不知道下一个用户会用什么奇怪的方式描述自己的问题。真正的用户永远会找到你测试集之外的 Case。

所以现在让我重新理解「上线」这个词，我反而觉得它并不像一个项目的终点。它更像是：**你终于把产品放进了真实世界，然后真实世界开始帮你测试它。**

所以真正重要的，也许从来不是做出一个永远不会失败的系统——这种系统大概也不存在。而是：**当它失败的时候，你能不能知道它为什么失败。** 以及，**能不能让下一次失败得少一点。**

## 六、Demo 到产品之间到底差了什么？

如果几个月前让我回答，我可能会说：UI、数据库、登录系统、部署、性能优化。这些当然都对。

但现在让我重新回答，我会觉得真正难的部分可能是：

**异常情况。能力边界。Fallback。测试。日志。数据。用户反馈。**

以及围绕这些东西不断发生的迭代。

前几天刚好发生了一件让我印象很深的事情。有一个用户反馈，我们产品的剪贴板功能有问题：**一用就闪退。** 听起来像是一个挺严重的 Bug。于是开始复现、排查，最后才发现——**他往剪贴板里复制了一万五千多行代码。**

看到这个结果的时候我其实有点绷不住。因为正常做功能、写测试的时候，我们当然会想到复制一句话、复制一段文字，可能也会测试比较长的文本。但「有一个用户会往剪贴板里塞一万五千多行代码」这种 Case，我大概很难在上线之前坐在工位上凭空想出来。

可问题是：**用户真的这么用了。** 而只要用户真的这么用了，它就不再是一个可以用「正常人谁会这么操作」带过去的问题。

对用户来说，他不关心我们的测试用例里有没有覆盖 15000 行代码。他只知道：**我复制了一段东西，然后你的产品崩了。**

这件小事反而让我更具体地理解了「真实用户」这四个字。我们总喜欢设计一个所谓的正常使用路径：用户会这样输入，会点击这个按钮，会按照这个流程操作，然后系统返回我们预期的结果。这就是 Demo 最擅长展示的东西——**Happy Path。**

但产品真正进入现实世界之后，用户会复制一万五千行代码，会发一句 `bro why dead`，会只扔给你一张截图和一个问号，也会做出无数你写测试用例的时候根本想不到的操作。

于是我现在越来越觉得：Demo 和产品真正的区别，可能不在 Happy Path 上。因为 Happy Path 往往在 Demo 阶段就已经做得很好了。真正拉开距离的，是它离开 Happy Path 以后会发生什么。

Demo 关注的是：

> **它成功的时候有多惊艳？**

而产品还必须关注：

> **它失败的时候有多难看？**

失败以后有没有日志？能不能定位问题？有没有兜底？会不会影响其他用户？这个 Case 会不会进入下一轮测试？下一次再有人复制一万五千行代码的时候，它还会不会崩？

这些事情不会出现在一段两分钟的 Demo 视频里。但它们可能才决定了一个东西能不能真的被人长期使用。

所以如果现在再让我回答：**一个 AI 功能从 Demo 到真的给用户用，中间差了什么？** 我可能不会再列一长串技术名词。我会说：**中间差的，是一个真实世界。** 以及一群永远不会按照你的 Demo 剧本使用产品的人。

## 七、再回头看 OpenSource Mentor

所以最近我重新打开 OpenSource Mentor 的时候，感觉其实挺奇怪的。它没有变——代码还是那些代码，功能还是那些功能：仓库分析、Issue 推荐、学习路线、导师对话、PR Review。

但看它的人已经有一点不一样了。以前我看到一个功能跑通，会觉得：**Nice，又完成一个功能。** 现在我会忍不住继续往下想：如果失败呢？怎么降级？怎么监控？用户到底有没有得到价值？什么数据能证明我的判断？下一次应该优化哪里？甚至，如果一个用户真的按照它推荐的路线开始参与开源，他最后走到了哪一步？

它依然是我很喜欢的一个项目。甚至可以说，正是因为做过这些 Demo，我才有机会走到后面的地方。所以我并不觉得 Demo 没有价值——恰恰相反。

**Demo 是我们把一个模糊想法变成现实最快的方式。** 一个想法原本只存在于脑子里。然后你写下第一行代码，接上第一个 API，让第一个 Agent 跑起来。直到某一刻，它真的动了。

只是现在的我不会再把「Demo 跑通」理解成终点。它更像程序员写下的第一句：

> Hello World.

你终于证明，这件事情是可以成立的。然后真正麻烦、也真正有意思的部分才刚刚开始。

[**OpenSource Mentor**](https://hokkai.top/) 现在依然可以使用。它最开始想解决的问题也没有变：**让一个不知道该如何参与开源的人，至少知道自己的第一步应该往哪里走。** 如果你最近也刚好面对着一个 GitHub 仓库发呆，不知道代码从哪里看、不知道哪个 Issue 适合自己，也不知道第一步应该干什么——可以去试试看。

现在再让我重新看这个项目，我最想验证的已经不只是：**「这个 AI 能不能分析一个仓库？」** 而是：**「它真的能不能让一个原本不知道怎么开始的人，完成自己的第一次开源贡献？」**

如果答案还不能确定，那它就还有很多东西可以继续做。而我大概也一样。

从第一个能跑起来的 Demo，到真正把东西交给用户；从关心「它能不能工作」，到开始关心「它失败了怎么办」；从不断给 AI 增加能力，到开始学习给它划清边界；从证明一个想法可以成立，到试着证明它真的有用。

现在回头看，OpenSource Mentor 好像还是原来的 OpenSource Mentor。**只是做它的人，已经往前走了一点。**
