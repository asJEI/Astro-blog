> **我知道 Harness，但我好像从来没有真正理解 Harness。**

今年四月，我参加过一场关于 Harness 的线上研讨会。那段时间它被讨论得很多，我也跟着看了一些，但说实话只能算浅尝辄止。

![四月份我待过的 Harness for AI coding 群](/images/blog/09/image-40.jpg)

Harness 直译过来是「鞍具」，我第一次接触这个概念时，理解也很直觉：

> **给 AI 套上一副更好的鞍具，让人能够更好地驾驭 AI。**

听起来很合理。但再往下看，我又觉得有点熟悉。Agent、MCP、Skills、工具调用、上下文、记忆……这些东西那时候已经铺天盖地。看了几篇文章和视频之后，脑子里最后留下来的印象甚至有点粗暴：**这不还是 Agent 吗？**

于是我没有继续研究。后来 Harness 的讨论慢慢淡出了我的信息流，我对它的认知也就一直停留在那里。中间偶尔再看到，也无非是 DeepSeek Harness 之类的东西，我依旧把它理解成一种更加完善的 Agent 框架。

直到几个月后的一场面试，对方突然问了我一句：

> **「你了解 Harness 吗？」**

我当然知道。甚至几个月前，我就已经待在一个专门研究 Harness 的群里。但真让我解释的时候，我发现自己能说出来的东西，居然和几个月前没什么区别。「大概了解过。我感觉和 Agent 差不多，只是 MCP、Skills 这些东西可能更加健全一些，没有深入体验过。」然后这个问题就过去了。

面试结束之后，我反而一直记着它。因为我突然意识到一个很尴尬的问题：我知道这个词，也见过相关的讨论，甚至待过专门研究它的群，可一旦要认真说清楚，我手里还是那句几个月前的话。于是我重新翻出当时看过的那些材料，也重新读了一遍 OpenAI 在二月发布的那篇 [《Harness engineering: leveraging Codex in an agent-first world》](https://openai.com/index/harness-engineering/)。

看完之后，我又想起了自己之前写的 [《Vibe Coding 指南》](/blog/vibe-coding-guide)。当时我试着用「道、法、术、器」总结自己使用 AI 编程的经验，其中有一个现在看起来很普通的方法，我把它叫作**上下文管理法**：在项目根目录建立 `.cursorrules`，或者维护一个 `memory-bank/`，把整体规划、开发要求和当前进度放进去；每天开工之前让 AI 先读一遍，结束之后再让它把今天做了什么、明天准备做什么写回去。这样做，无非是为了避免出现——**昨天还好好的，今天就像弱智一样**。

这些方法当然谈不上什么 Harness Engineering。它们更像是一个普通 Vibe Coder 为了让 AI 稳定工作，一点点摸索出来的办法。AI 会忘，那就给它准备 Memory；AI 会跑偏，那就写 Rules；项目太大容易乱，就先拆模块、定结构。但重新去看 Harness 时，我突然发现了一件很有意思的事情：

> **我们过去在 Vibe Coding 里靠经验、靠习惯、靠人肉维护的很多东西，正在被写进 Agent 所处的环境里。**

而这可能才是我几个月前没有看懂的地方。Harness 想解决的，从来不只是「怎么让 AI 更聪明」，而是：**当 AI 已经足够聪明以后，怎么让它真正把一件事情做完？** 这一次，我想从这里重新聊聊它。

---

## 一、模型负责聪明，Harness 负责让它工作

重新去看 Harness 时，我觉得最需要先想清楚的一件事，是模型和 Agent 到底是不是一回事。以前我很容易把两者混在一起。GPT、Claude、Gemini 这些模型越来越强，能理解更复杂的需求，也能写越来越长的代码，于是一个很自然的想法就是：只要模型足够聪明，Agent 自然也会越来越强。

但实际用久了就会发现，好像不是这么回事。**一个模型可能很聪明，但它组成的 Agent 依然很蠢。** 这种情况我自己遇到过很多次。比如用 Cursor 或者 Codex 写一个稍微大一点的项目，前面明明聊得很好，它也知道整个项目要做什么；结果开了一个新窗口，或者中间某一次执行出了问题，上下文突然没接上，然后它就开始乱改。模型其实没有变笨。你用的还是同一个模型，它写代码、分析问题、理解自然语言的能力也没有突然下降。但 Agent 确实在那一刻「变笨了」——因为它不知道自己在哪里，不知道之前做了什么，不知道项目有什么约束，不知道接下来该干什么，甚至不知道哪些东西不能碰。

这也是为什么以前我会使用 `.cursorrules` 和 `memory-bank`。本质上，我是在人工给这份智能补一个工作环境：这是我们的项目，这是我们的目标，这是之前完成的东西，这是你需要遵守的规则，这是接下来要做的事情。所以重新理解 Harness 之后，我脑子里逐渐形成了一个很简单的区分：

> **Model 提供智能，Harness 指引智能。**

模型决定的是它有没有能力解决这个问题；Harness 决定的则是这份能力能不能在一个真实项目里持续、稳定地发挥出来。这也是为什么我现在更愿意把 Harness 理解成一种 Agent 的「操作系统」。当然，这只是一个方便理解的比喻。

一个再聪明的人，如果你把他丢进一家完全陌生的公司，不告诉他项目背景，不给他代码仓库，不给他开发工具，不告诉他权限边界，也没有测试和反馈机制，然后只说一句「开始工作吧」，他大概率也不知道该干什么。Agent 也是一样。它需要 Context，知道自己正在处理什么；需要 Memory，知道之前发生过什么；需要 Rules，知道什么能做、什么不能做；需要 Tools，真正读取文件、搜索代码、执行命令；还需要 Test 和 Feedback，知道自己刚才做的到底对不对。

这些东西单独拿出来，其实都不新鲜。Context 我们早就在聊，Memory 也早就在聊，MCP、Skills、Tool Calling 更不用说。真正让我重新理解 Harness 的地方在于：

> **Harness 的重点可能从来不是发明一个新的能力，而是把这些能力组织起来，让模型拥有一个可以持续工作的环境。**

所以现在再回头看「鞍具」这个翻译，我反而觉得挺形象。马本身跑得快不快，是马的能力。Harness 并不会让一匹马凭空跑得更快，但它决定了骑手能不能控制方向，能不能把力量传递出去，能不能真的骑着它到达目的地。对于 Agent 也是一样。

**模型负责聪明。Harness 负责让这份聪明真正开始工作。**

但到这里，其实还只是解决了「怎么让 Agent 正常工作」的问题。我真正期待的东西还要再往前一步。因为我并不想每天给 AI 准备好所有任务，然后一句一句告诉它先做这个、然后做那个、跑一下、报错了检查一下、再测试一下。如果这些事情最后还是需要我一步一步推动，那么所谓的 Agent，似乎依然只是一个更高级的工具。

**我真正想要的，是给它一个目标，然后让它自己把事情做完。**

## 二、我想要的不是「会写代码」，而是「把事情做完」

说实话，我对 AI Coding 的期待一直不只是「帮我写代码」。我真正想要的状态其实很简单。比如有一天我突然想到，想要一个可以统计某某数据的网页。我把这个想法告诉 AI，然后就没了。接下来它应该自己理解我要做什么，根据目标拆解任务，制定一个大致的开发计划；需要查资料就去搜索，需要读取项目就读取文件，需要安装依赖就安装依赖，需要写代码就写代码。代码写完以后自己运行，报错了自己看日志，发现问题自己修改，修改完继续测试，直到最后，一个至少能用的 V1 出现在我面前。整个过程大概是：

`Goal → Plan → Task → Tools → Code → Test → Feedback → Retry → V1`

![Human 给出目标，Agent Loop 自主完成到 V1，再用体验重新定义下一轮](/images/blog/09/image-41.png)

这才是我理解中更接近「高级智能」的东西。因为现在很多时候，我们虽然已经在说 Agent，但真正使用起来，人依然承担了大量的调度工作。AI 写完一段代码，我说「运行一下」；运行报错，我再说「看看报错是什么原因」；它修完，我又说「测试一下其他情况」；测试发现问题，我继续说「这里不对，再改」。看起来是 AI 在写程序，但仔细想想，整个工作流真正的 Planner、Scheduler 和 Evaluator 其实还是人。

**人脑才是那个隐藏在 Agent 背后的 Harness。**

我们负责记住目标，负责判断下一步应该干什么，负责把错误重新喂回去，也负责在它跑偏的时候把它拽回来。AI 只是在一个又一个局部任务里执行。这也是为什么我现在觉得：

> **「AI 能写代码」和「AI 能完成一个项目」，其实是两件完全不同的事情。**

前者主要依赖模型能力。模型越聪明，它越能理解需求、生成代码、分析 Bug。但后者还需要另一个东西：**一个能够让智能持续运行下去的闭环。** 它需要知道当前目标是什么，把目标拆成任务，知道自己拥有哪些工具；执行之后观察结果，结果不符合预期就重新规划或者 Retry，直到满足某个可以被验证的完成条件。

如果把这个过程拆开来看，会发现 Harness 真正开始发挥作用的地方，恰恰就是这些以前需要人类不断介入的环节。以前是 `Human → AI → Human → AI → Human → AI`，人类不停充当两个 AI Action 之间的连接器。而我期待的状态更接近 `Human → Agent Loop → V1`：人只需要在一开始给出目标，中间的 Planning、Execution、Tools、Test、Feedback 和 Retry，由 Agent 自己完成。

当然，这并不意味着人类从开发中消失了。因为这里有一个很重要的词：**V1**。Agent 可以根据我的要求，把一个项目从 0 跑到 V1；但 V1 做出来之后，我还是要真的去用它。也许用了五分钟，我就会发现这个功能根本没有我想象中那么重要，这个交互虽然能用但是很难用，我一开始想统计 A，真正用起来以后却发现自己更关心 B。然后我会重新修改自己的目标，再让 Agent 去做 V2。

所以真正完整的循环并不是 `Human → Agent → Finished`，而更像是：

`Human → Define → Agent → V1 → Experience → Redefine → Agent → V2 → ...`

Harness 并没有把人从这个循环里赶出去。它真正改变的是：

> **人正在从执行的小循环里退出，回到产品迭代的大循环里。**

我们以前总结出来的很多「技巧」，好像正在从人的经验，变成 Agent 的工程。

## 三、从 Vibe Coding 的「法」，到 Harness Engineering

重新理解 Harness 之后，我又回去看了一遍自己之前写的《Vibe Coding 指南》。那篇文章里，我把 AI 编程分成了四层：**道、法、术、器**。

所谓「道」，是我认为最底层的东西。当时我写的是：**人类定义问题，AI 解决问题。目的主导，上下文优先，结构先行。** 「法」则是为了做到这件事，我总结出来的一些方法，比如提示词自我迭代、上下文管理、模块化开发。「术」再往下一层，是具体怎么操作：怎么写 Prompt，怎么交互式 Debug，AI 看不懂的时候怎么截图给它，出现问题以后怎么把报错重新喂回去。最后是「器」。Cursor、Codex、VS Code，甚至再往前一点的 VC6++，这些都是工具。

几个月后重新看这套东西，我发现一个很有意思的变化。**「道」其实没有怎么变。** 我现在依然认为，人最重要的工作是定义问题。**「器」也没有发生本质变化。** 工具当然越来越强，但它依然是工具。真正开始发生剧烈变化的，反而是中间的「法」和「术」。

以前为了防止 AI 忘记项目，我会维护一个 `memory-bank/`，这是「法」；为了保证它每次真的读取，我会在开工前主动告诉它先读取记忆文件、同步项目上下文，这是「术」。以前 AI 写完代码，我需要主动让它运行、测试，报错以后再把日志或者截图交给它，修完以后再提醒它重新验证，这些也都是「术」。换句话说，过去 Vibe Coding 很大一部分能力，其实存在于**使用 AI 的那个人身上**。你需要知道什么时候该补 Context，什么时候该开一个新的对话，什么时候该让它先别写代码、而是先 Planning，什么时候应该拆模块，什么时候应该跑测试，什么时候 AI 已经开始胡说八道、需要停下来重新同步上下文。我们把这些东西总结成「技巧」。然后一个人用 AI 用得多了，就会越来越「会用 AI」。

但 Harness Engineering 给我的一个很强烈的感觉是：

> **这些原本存在于人脑里的经验，正在被一点点写进系统。**

以前是我记得让 AI 读取 Memory，现在可以让 Context 和 Memory 本身成为 Agent 工作环境的一部分；以前是我记得告诉 AI 项目的规则，现在可以把 Rules 直接放进 Repository，让 Agent 每次工作时都能够读取；以前是我发现报错、把报错发给 AI、让它修改、再让它运行，现在这个过程可以变成 `Execute → Observe → Feedback → Retry`；以前是我记得让它测试，现在测试本身可以成为完成任务之前必须经过的 Verification。这也是为什么我现在越来越觉得：

> **Harness Engineering 做的一件很重要的事情，就是把 Vibe Coding 的经验变成工程。**

当然，这并不是说 `.cursorrules`、Memory、Tools 或者测试是什么 Harness 发明的新东西。恰恰相反，这些东西很多早就存在。真正发生变化的是：**过去它们是一些散落的方法，现在它们开始被组织成一套让 Agent 可以持续工作的环境。**

以前一个人 Vibe Coding 的上限，很大程度上取决于「你有多会使用 AI」。而 Harness Engineering 想做的事情，可能是在慢慢减少这种依赖。不是要求每一个人都记住一百条「如何正确使用 AI」的技巧，而是把这些已经被验证有效的经验，变成 Rules、Memory、Tools、Skills、Tests 和 Feedback Loop，让它们成为 Agent 工作方式的一部分。

当时我只是单纯不想让 AI 昨天还好好的、今天就像弱智一样，所以自己维护了一套 Memory。但如果有一天，记忆不再需要我维护，规则不再需要我提醒，测试不再需要我发一句「你跑一下」，报错之后也不需要我手动把错误重新喂回去——那时候变化的可能不只是 AI Coding 的效率，而是我们和 AI 之间的分工。因为当越来越多的「法」与「术」被写进 Harness 以后，人真正需要负责的东西，反而会越来越往上走。最后留下来的，可能恰恰又回到了最开始的那个「道」：

> **目的主导，结构先行。人类定义问题，AI 解决问题。**

但这里又会出现一个新的问题。如果以后我真的只需要说一句「帮我做一个 XXX」，Agent 就能自己完成规划、开发、测试，最后把一个 V1 放到我面前——**那人还需要会什么？**

## 四、当 AI 可以自己做完 V1，人还需要做什么？

如果 Harness 继续发展下去，我觉得 AI Coding 最终会越来越接近这样一种状态：我有一个想法，在真正开始之前先告诉 Agent 我要做一个什么东西，然后它自己规划、拆解、开发、测试，最后把一个可以运行的 V1 交给我。听起来，人需要做的事情越来越少了。但我自己的感觉反而是：**越是这样，开始之前的「事前架构」就越重要。**

这里说的架构，并不完全是传统软件工程里的 Architecture。我不是说在 Agent 开始工作之前，人还得先把数据库怎么设计、接口怎么定义、前端用什么框架、每个模块怎么实现全部想清楚。如果这些东西都要我提前设计完，那 Agent 也没有帮我省下多少事情。我说的「事前架构」更像是：

> **在真正开始创作之前，我脑子里应该先大致预演出这个 V1。**

我可以不知道它具体怎么实现。但我至少应该知道：我到底想做什么？它最核心的问题是什么？第一版应该有哪些东西，哪些东西这一版可以不要？用户大概会怎么使用它？最后做到什么程度，我会认为这个 V1 已经完成？也就是：

**How 可以交给 Agent，但 What 不能完全交给 Agent。**

这其实也是我现在使用 Cursor、Codex 时越来越明显的一个习惯。我很少上来就直接让 AI 开始写。通常我会先规划，先想清楚项目大概是什么、要解决什么问题、第一版需要做到哪里，再把这些东西写进项目的规则、Memory 或者 Plan 里，然后才让 Agent 开始执行。因为 AI 的执行能力越强，一个模糊目标带来的问题反而可能越大。

以前自己写代码的时候，方向错了可能半天才写几百行。写着写着发现不对，这个东西好像不是我想要的，停下来改就行。但如果 Agent 可以自己连续工作几个小时，它完全可能在一个错误的方向上非常勤奋地规划、建库、写代码、补页面、跑测试、修 Bug，最后交给你一个完成度非常高的东西。然后你打开一看：

> **「做得挺好，但这根本不是我想要的。」**

这可能会成为 AI Coding 里一个越来越常见的问题。**AI 可以非常高效地实现一个错误的 V1。** 而 Harness 越完善，这种能力反而越强。因为 Harness 解决的是如何让 Agent 更可靠地朝着一个目标执行，但它并不能天然保证这个目标本身就是对的。这件事最后还是会回到人身上。

所以我不太认同一种想象：以后 AI 什么都能做，所以人只需要有一个 Idea 就够了。Idea 太便宜了。「我想做一个 AI 社交产品。」「我想做一个自动赚钱的网站。」「我想做一个统计 XXX 的工具。」这些都只能算一个模糊的念头。真正困难的是继续往下想：它到底是什么？为什么有人需要它？V1 最小应该做到哪里？什么才算做成了？当执行越来越便宜以后，这些问题反而会越来越重要。

但即便这些问题在开始之前都想清楚了，我依然不认为 Agent 做出来的东西就是最终答案。因为我脑子里预演出来的 V1，也可能是错的。所以 Agent 把 V1 做出来之后，我还是要自己去用。真的点一遍，真的跑一遍，真的把它放到用户面前。然后你很可能会发现，这个功能我原来觉得很重要，实际上根本没人用；我原来以为用户会这么操作，结果大家根本不是这么用的；甚至产品确实按照我的要求做出来了，但我的要求本身就错了。于是重新修改目标，再做 V2，再体验，再修改。

所以我理解中的未来开发流程，并不是 `Idea → Agent → Product`，而更像是：

`事前架构 → V1 → 真实体验 → 重新定义 → V2 → 再体验 → V3...`

Agent 可以把其中每一次从目标到版本的执行周期压缩得非常短，Harness 可以让这个执行周期越来越自主。但**定义、体验、判断、重新定义**，依然构成了外面那个更大的循环。换句话说：

> **Harness 让人逐渐退出执行的小循环，但没有让人退出产品迭代的大循环。**

反而因为执行变快了，人可以把更多精力放回这些事情上。这也是为什么，绕了一大圈之后，我发现自己几个月前写下的那句话好像还是没有变：**目的主导，结构先行。** 以前结构先行，是因为代码写错了很贵；以后结构先行，可能是因为 **AI 把错误的东西做得太快了。**

---

## 五、人类掌舵，智能体执行

重新看完 Harness Engineering 之后，我又想起了 OpenAI 那句话：

> **Human steers. Agents execute.**
>
> **人类掌舵，智能体执行。**

我们一直在讨论 **AI 还能替人做什么？** 但如果这些事情真的逐渐被 Agent 接过去，剩下来的那个问题反而变成了：**人应该负责什么？**

我现在的答案其实没有几个月前想象得那么复杂。还是我在那篇《Vibe Coding 指南》里写过的那句话：

> **人类定义问题，AI 解决问题。**

只是几个月前写下它的时候，这更像是一种理想状态。因为那时候所谓的「AI 解决问题」，中间其实夹着大量的人类工作：定义问题、拆解任务、准备上下文、提示 AI、检查结果、Debug、测试、再提示 AI……我们嘴上说 AI 在解决问题，但很多时候，人自己才是那个真正维持整个系统运转的 Harness。

而现在，这些中间环节开始被一点点工程化。以前需要我记住的东西，可以变成 Memory；以前需要我反复强调的要求，可以变成 Rules；以前需要我手动触发的操作，可以变成 Tools；以前需要我发现错误再告诉 AI，可以变成 Test、Feedback 和 Retry。

所以写到最后，我反而不觉得 Harness Engineering 是在讨论「怎么把人从软件开发里删掉」。它更像是在重新划分人和 AI 的边界。**AI 往执行的深处走，人往问题的上游走。** 而当越来越多执行层面的「法」与「术」被写进 Harness，真正留给人的，可能恰恰是那些最开始就应该想清楚的东西：为什么做？做什么？做到什么程度？做出来以后，它真的是我想要的吗？

这也是为什么，隔了几个月重新回头看，我发现自己原来那套「道、法、术、器」并没有被推翻。「器」越来越强，「术」正在被自动化，「法」正在被工程化，而最后剩下来的「道」，似乎还是那几个字：

> **目的主导，上下文优先，结构先行。**

Harness 不会替你决定要去哪里。它只是让一个足够聪明的 Agent。未来真正稀缺的，不再是「怎么让 AI 帮我把这个东西做出来」，而是当你拥有一个越来越能自主完成工作的 Agent 时——

**你究竟知不知道，自己想让它做出什么。**
